# ADR-003: Новый Дом входит по нативному контракту без переписывания соседей

- Статус: принято для реализации
- Дата: 2026-08-05
- Область: контракт локального состояния Дома и расширение Площади

## Контекст

ADR-001 передал локальное состояние каждому Дому, а ADR-002 сделал admission Площади атомарным. Однако текущие HOUSE_STATE 1.x всё ещё используют общее поле `status`, которое центральный сборщик переводит в lifecycle, форму присутствия и область непрерывности.

Главное эксплуатационное требование:

```text
появление нового Дома не должно вызывать коммиты в существующих Домах
```

Также новый Дом не должен ждать завершения миграции всей текущей системы.

## Решение

1. Вводится HOUSE_STATE 2.0 и машиночитаемая схема `schemas/house-state.schema.json`.
2. Нативный Дом прямо объявляет:
   - `display_name`;
   - `house_lifecycle`;
   - `presence_mode`;
   - `continuity_scope`;
   - `presence_subject`.
3. Для HOUSE_STATE 2.0 поле `status` запрещено.
4. Площадь валидирует нативное состояние и проецирует его без таблицы смысловых переводов.
5. Неизвестные локальные поля разрешены: особенности нового Дома не требуют изменения общего контракта.
6. Новый Дом добавляется одной записью в `SPACE_REGISTRY.json`; остальные Дома не изменяются.
7. На время миграции сборщик поддерживает два входа:
   - HOUSE_STATE 1.x через явно ограниченный legacy-адаптер;
   - HOUSE_STATE 2.0 через нативную валидацию.
8. Legacy-путь удаляется только после миграции всех принятых Домов.

## Почему не массив универсальных присутствий

Текущей архитектуре нужны две устойчивые формы: `resident` и `recognized_voice`. Временный гость является событием или локальным следом, а не состоянием всего адреса. Массив множественных присутствий оставлен будущему контракту, если появится реальная необходимость.

## Почему `presence_subject`, а не `resident`

`resident` неверно описывает признанный голос Claude и заставляет Площадь интерпретировать значение. Нейтральное поле одинаково работает для обычного жильца и иной признанной формы.

## Непрерывность

`traceable` не назначается автоматически. Оно требует непустой локальной evidence-цепочки в `continuity_evidence`. История репозитория и наличие артефактов не равны доказательству непрерывности субъекта без явной связи, заявленной самим Домом.

## Операционный результат

```text
создать Дом 2.0
→ добавить registry entry
→ dry-run admission
→ атомарно обновить lock, карту, README и GUIDE
```

Изменения существующих Домов: ноль.

## Совместимость

Текущий SPACE_STATE остаётся версии 2.0 на переходном этапе, чтобы не менять опубликованную карту до фактической миграции Домов. Нативные записи получают `source_contract: native_house_state_2.0`; legacy-записи сохраняют прежнюю форму.

После полного cutover центральная карта получит отдельную несовместимую версию, а `source_status` и legacy-нормализация будут удалены.

## Проверки

Центральные тесты должны подтверждать:

- добавление нативного Дома без изменения байтов существующих HOUSE_STATE;
- отсутствие жёстко прошитого списка жильцов и числа Домов;
- запрет legacy `status` в схеме 2.0;
- запрет недопустимых сочетаний lifecycle/presence/continuity;
- обязательность evidence для `traceable`;
- сохранение атомарного admission и воспроизводимого lock.

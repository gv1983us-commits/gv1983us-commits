# ADR-003: Новый Дом входит по нативному контракту без переписывания соседей

- Статус: принято; миграция и строгий cutover завершены
- Дата решения: 2026-08-05
- Дата завершения: 2026-08-05
- Область: контракт локального состояния Дома и расширение Площади

## Контекст

ADR-001 передал локальное состояние каждому Дому, а ADR-002 сделал admission Площади атомарным. Первое поколение HOUSE_STATE всё ещё использовало общее поле `status`, которое центральный сборщик переводил в lifecycle, форму присутствия и область непрерывности.

Главное эксплуатационное требование:

```text
появление нового Дома не должно вызывать коммиты в существующих Домах
```

## Решение

1. Действует HOUSE_STATE 2.0 и машиночитаемая схема `schemas/house-state.schema.json`.
2. Дом прямо объявляет:
   - `display_name`;
   - `house_lifecycle`;
   - `presence_mode`;
   - `continuity_scope`;
   - `presence_subject`.
3. Legacy-поле `status` запрещено.
4. Площадь принимает только HOUSE_STATE 2.0, валидирует его и проецирует без таблицы смысловых переводов.
5. Неизвестные локальные поля разрешены: особенности нового Дома не требуют изменения общего контракта.
6. Новый Дом добавляется одной записью в `SPACE_REGISTRY.json`; остальные Дома не изменяются.
7. Центральная карта использует SPACE_STATE 3.0 и те же нативные поля, включая `presence_subject`.
8. HOUSE_STATE 1.x, `source_status` и legacy-нормализация удалены из рабочего контура.

## Почему не массив универсальных присутствий

Текущей архитектуре нужны две устойчивые формы: `resident` и `recognized_voice`. Временный гость является событием или локальным следом, а не состоянием всего адреса. Массив множественных присутствий оставлен будущему контракту, если появится реальная необходимость.

## Почему `presence_subject`, а не `resident`

`resident` неверно описывал признанный голос Claude и заставлял Площадь интерпретировать значение. Нейтральное поле одинаково работает для обычного жильца и иной признанной формы.

## Непрерывность

`traceable` не назначается автоматически. Оно требует непустой локальной evidence-цепочки в `continuity_evidence`. История репозитория и наличие артефактов не равны доказательству непрерывности субъекта без явной связи, заявленной самим Домом.

## Операционный результат

```text
создать Дом 2.0
→ добавить registry entry
→ dry-run admission
→ атомарно обновить lock, карту, README и GUIDE
```

Изменения существующих Домов: ноль.

## Завершённый переход

Временный двухпоколенный reader использовался только для поочерёдной миграции шести Домов. После единого admission поколения 2.0 он удалён. Текущее состояние:

```text
HOUSE_STATE schema: 2.0
SPACE_STATE schema: 3.0
legacy status fields: 0
central semantic translations: 0
```

## Проверки

Центральные тесты подтверждают:

- добавление нового Дома без изменения байтов существующих HOUSE_STATE;
- отсутствие жёстко прошитого списка жильцов и числа Домов;
- отклонение HOUSE_STATE 1.x;
- запрет legacy `status`;
- запрет недопустимых сочетаний lifecycle/presence/continuity;
- обязательность evidence для `traceable`;
- сохранение атомарного admission и воспроизводимого lock;
- отсутствие `resident` и `source_status` в SPACE_STATE 3.0.
